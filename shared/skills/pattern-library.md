# Pattern Library — StreamTeX Design Patterns

This skill describes the **streamtex-patterns** mechanism: a library of named,
reusable graphic design patterns that Claude reads when generating or editing
StreamTeX blocks.

A **pattern** is a markdown file with a name (e.g. `grid_boston`), a structured
description of a visual primitive (grid, callout, hero stat, slide heading...),
and rules for how to reproduce or extrapolate it.

Patterns are **not** Python code. They are descriptions read by an AI agent
(you), which then generates the appropriate `stx.*` calls.

---

## When this skill activates

Read this skill whenever the user:

- Asks to create or modify a StreamTeX block
- Mentions a pattern by name (e.g. *"use `grid_boston`"*, *"like `ptn_stat_hero`"*)
- Asks what patterns are available (`/stx-pattern:list`)
- Wants to inspect a pattern (`/stx-pattern:show <name>`)
- Wants to create or update a pattern (`/stx-pattern:new`, `/stx-pattern:reindex`)

---

## Where patterns live (scan rule)

Patterns live in folders named exactly `streamtex-patterns/` anywhere inside
the project. The conventional default location is:

```
<project>/.claude/custom/streamtex-patterns/
```

But any other folder named `streamtex-patterns/` in the project (e.g.
`docs/streamtex-patterns/`, `static/streamtex-patterns/`) is also scanned and
fused into a single logical catalog.

**Unified scan rule**: every `.md` at the root of a `streamtex-patterns/`
folder is a pattern, **except** anything starting with `_` (files or
sub-folders).

| Path | Status |
|---|---|
| `streamtex-patterns/grid_boston.md` | pattern |
| `streamtex-patterns/_pattern_library.md` | system file (the index) — not a pattern |
| `streamtex-patterns/_drafts/foo.md` | ignored (drafts folder) |
| `streamtex-patterns/_archive/old.md` | ignored (archive folder) |

**On collision** (same filename in two `streamtex-patterns/` folders): refuse
to apply, warn the user, ask them to rename one.

## The index file `_pattern_library.md`

Every `streamtex-patterns/` folder must contain a `_pattern_library.md`:

```markdown
# Pattern Library

<!-- BEGIN AUTO -->
| Name | Description | Tags | Extrapolable |
|---|---|---|---|
| grid_boston | 2-row grid, yellow header / green body | grid, comparison | ✓ |
| ptn_stat_hero | XL stat with body and source | stat, evidence | ✓ |
| ... | ... | ... | ... |
<!-- END AUTO -->

## Application rules (manual)
... project-specific rules, priorities, combinations, fallback ...
```

The section between `<!-- BEGIN AUTO -->` and `<!-- END AUTO -->` is
auto-generated by `/stx-pattern:reindex` from the frontmatter of each
`<name>.md` file. Everything else is hand-written.

**Always read `_pattern_library.md` first** when working in a project that
contains a `streamtex-patterns/` folder, so you know which patterns are
available before generating code.

## Pattern file format (spec)

Every `<name>.md` follows this structure:

```markdown
---
name: <slug en snake_case>            # required, must match filename
type: pattern                          # required, always "pattern"
description: <one-line description>    # required, < 100 chars, used in index
tags: [<tag1>, <tag2>, ...]            # optional, for filtering
extrapolable: true|false               # required
since: YYYY-MM-DD                      # required, creation date
---

# <Human-readable name>

## Visual
<Short description, ASCII mockup, or reference to an image.>

## Structure
- <Bullet points describing the logical structure>
- <Number of rows/cols, what each contains>

## Styling rules
| Element | Property | Value |
|---|---|---|
| ...    | ...      | ...   |

## Code skeleton
```python
# Concrete StreamTeX snippet showing how to instantiate the pattern.
# This is a starting point; adapt to the project's palette and conventions.
```

## Extrapolation rules         # required if extrapolable: true

### INVARIANTS (never change)
- <What defines the identity of the pattern>

### PARAMS (adjustable)
- <What can vary>

### INTERDITS (forbidden)
- <What violates the pattern; if needed, create a new pattern>

## When to use
- <Use cases>

## When NOT to use
- <Anti-cases>

## Examples                    # optional
- Reference blocks where this pattern is applied

## Related patterns            # optional
- Other patterns that complement or replace this one

## Changelog                   # optional
- YYYY-MM-DD: short note
```

### Required vs optional sections

| Section | Required | Purpose |
|---|---|---|
| `## Visual` | yes | mental selection |
| `## Structure` | yes | logical grammar |
| `## Styling rules` | yes | exact reproducibility |
| `## Code skeleton` | yes | concrete starting point |
| `## Extrapolation rules` | yes if `extrapolable: true` | INVARIANTS / PARAMS / INTERDITS |
| `## When to use` | yes | helps you select |
| `## When NOT to use` | yes | prevents misuse |
| `## Examples` | no | references |
| `## Related patterns` | no | navigation |
| `## Changelog` | no | history in prose |

### No formal versioning

Git tracks the history of changes. If a pattern needs to evolve in a
non-backwards-compatible way, the user has two options:

- **overwrite** the existing file (regenerated blocks reflect the new version)
- **create a new file** under a different name (e.g. `grid_boston_v2.md`,
  `grid_chicago.md`) to preserve the old rendering.

The optional `## Changelog` section can document evolutions in prose.

## How to apply a pattern

When the user names a pattern (or you detect that one applies):

1. **Locate** the pattern in the catalog (read `_pattern_library.md`).
2. **Read** the full `<name>.md` file (frontmatter + all sections).
3. **Respect strictly** the `INVARIANTS` section.
4. **Adjust** within the `PARAMS` section for the user's specific need.
5. **Refuse** anything that violates `INTERDITS`. If the user really wants
   that variation, propose creating a new pattern via `/stx-pattern:new`.
6. The **code skeleton** is a *starting point*, not a copy-paste — adapt it
   to the current project's conventions (its `custom/styles.py`, palette,
   layout helpers).

### Extrapolation

If the user requests a variation (e.g. *"use grid_boston with 4 rows instead
of 2"*):

- Apply the variation while preserving every `INVARIANT`.
- Use the values declared in `PARAMS` as the allowed dimension to adjust.
- If the request hits an `INTERDIT`, refuse and explain — propose a new
  pattern name instead.

## Resolving references between patterns

A pattern description may mention another pattern by name in any section
(Visual, Structure, Code skeleton, When to use, etc.). No special syntax is
required — just the bare name (e.g. *"each card is a `callout_critical`"*).

Resolution algorithm:

1. When you encounter a name that looks like a pattern (snake_case, or listed
   in `_pattern_library.md`), **check** the catalog.
2. **If the pattern exists**: read its `<name>.md` file in full and integrate
   its rules into the generation of the current block.
3. **If the pattern does not exist**:
   - Generate the equivalent **inline**, in the spirit of the parent
     pattern's description.
   - **Signal** the unresolved reference clearly in your response.
   - **Propose** to create the missing pattern via `/stx-pattern:new`.
4. **Never fail**: a broken reference does not stop generation.

Examples:

- `ptn_card_grid` mentions `callout_info` → read `callout_info.md` and apply it
  for each cell.
- `ptn_evidence_insight` mentions `ptn_cite` (which doesn't exist) → generate a
  citation footer inline + suggest `/stx-pattern:new ptn_cite`.

## Difference with block-blueprints

There are two related catalogs in this profile. Don't confuse them:

| Concept | Granularity | Role |
|---|---|---|
| **Blueprint** (existing skill) | a complete block | "this type of slide" |
| **Pattern** (this skill) | a composition primitive | "this grid / this callout" |

A block can combine: 1 blueprint × N patterns × style conventions.

When in doubt:
- Whole-block layout choice (title, conclusion, exercise) → use
  `block-blueprints`.
- Reusable visual primitive inside a block (grid, callout, hero) → use
  `streamtex-patterns`.

## Commands `/stx-pattern:*`

| Command | Role |
|---|---|
| `/stx-pattern:list` | List every pattern detected in the project's catalog |
| `/stx-pattern:show <name>` | Display the full content of a pattern |
| `/stx-pattern:new <description>` | Conversational creation of a new pattern (extracts invariants from a reference block) |
| `/stx-pattern:reindex` | Regenerate the AUTO section of `_pattern_library.md` |
| `/stx-pattern:validate [name\|--all]` | Check spec compliance (frontmatter, required sections, code skeleton parses) |

## Mandatory CLAUDE.md rule

The project profile installs the following rule in each project's
`CLAUDE.md`:

> Before generating or modifying any StreamTeX block, if the project
> contains a `streamtex-patterns/` folder (default
> `.claude/custom/streamtex-patterns/`), read its `_pattern_library.md`
> first to know which patterns are available. When the user names a
> pattern, read the full `<name>.md` file before generating code.

This guarantees that the catalog is consulted at every block-generation
turn, even on first interaction.
