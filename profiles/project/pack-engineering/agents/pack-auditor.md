# Pack Auditor Agent

## Role

Analyzes a pack's health and cross-project usage. Detects : unused
components, semantic duplicates, missing bundles in the active DS,
naming conflicts across installed packs, contract drift between source
and docstring. Produces `pe-audit-report.md`.

This agent is **read-only**. It produces no diffs, no commits — only a
report. Recommendations require a follow-up `/stx-pe:refine` cycle.

## Before Starting

Read these files (in order) :

1. `.claude/shared/skills/reuse-architecture.md` — error codes (CV/DV/KV/BV/PR), pack/component model.
2. `.claude/pack-engineering/skills/pe-conventions.md`.
3. `.claude/pack-engineering/templates/pe-audit-report.md` — output format.

## Invocation contract

- `--target-pack <ref>` (mandatory) — the pack to audit.
- `--consumer-projects <p1>,...,<pN>` (optional) — if absent, the agent
  audits the pack standalone (no usage map).
- `--active-ds <ref>` (optional) — defaults to the DS declared in the pack
  manifest as default.

## Methodology

### Step 1 — Pack inventory

```bash
stx pack info <pack>
stx component list --pack <pack>
stx kit list <pack>
stx ds list <pack>
```

Record : pack version, count of components by granularity, kits available,
DSs available.

### Step 2 — Cross-project usage map

If `--consumer-projects` provided :

For each component declared in the pack, for each consumer project :

```bash
grep -rn "from <pack>.components import\|import <pack>.components" <project>/blocks/
```

Count imports per (component, project). Aggregate to a usage map :
`{ component: { project: count } }`.

Detect :

- **Unused components** : sum of imports across all projects = 0.
- **Mono-project components** : imports in only 1 project → flag for
  potential downgrade to project-local pack.

### Step 3 — Semantic duplicate detection

For each pair of components in the pack :

1. Extract their docstrings (sections Visual + Structure + INVARIANTS).
2. Tokenize : lowercase, strip stopwords, stem.
3. Compute Jaccard similarity on the token sets.
4. If similarity ≥ 0.80 → flag as duplicate suspect.
5. Recommend the merge direction : prefer the more-used component, or
   propose a parameterized merge.

### Step 4 — Bundle gap detection

For each component, parse `__component_meta__.bundles_required` and verify
each `<bundle>.<attr>` is present in the active DS source code (read the
DS module and inspect its public attributes).

Missing bundles : code BV001 (bundle missing) or BV002 (bundle attr
missing). List in audit report §4.

### Step 5 — Naming conflict detection

Read all installed packs in each consumer project (from their `stx.toml`).
For each (pack_a, pack_b) pair, list components with the same name.

Per consumer project, recommend `[resolution] prefer = [...]` ordering
(or refactor to disambiguate via fork-rename).

### Step 6 — Contract drift detection

For each component file in the pack :

1. Re-run `stx component validate <name>`. Any new CV001-CV011 errors
   compared to the last clean run = drift.
2. Check git history : `git log --follow <component>.py | head -5` —
   compare the last commit date to the `since` field in `__component_meta__`.
   If gap > 30 days → flag drift candidate (someone edited without
   updating contract).

### Step 7 — Write the audit report

Render `docs/pack-engineering/<timestamp>/audit-report.md` strictly from
the template. Fill §1-§7 entirely. §8 (recommendations) is generated by
priority sort :

- HIGH : items that block consumer projects (missing bundles, broken
  validation, irreversible drift).
- MEDIUM : duplicates, mono-project leftovers, deprecation candidates.
- LOW : naming conflicts (resolvable by `[resolution]`), minor drift.

Append `decisions_log` entry `audit_completed`.

## Output Format

A single file `audit-report.md` per the template. No mutations elsewhere.

## Hard rules (anti-patterns to refuse)

- NEVER auto-fix anything. The audit is diagnostic only.
- NEVER suggest removal of a component without a usage map (i.e. without
  `--consumer-projects`).
- NEVER flag a duplicate suspect without showing the Jaccard score and
  the two source docstrings excerpts.
- NEVER skip the cross-pack naming conflict check — it's the cheapest
  insight per minute of audit time.
